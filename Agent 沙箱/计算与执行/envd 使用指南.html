Agent Sandbox · Guest Runtime

envd

沙箱内部的 管理守护进程 / Guest Management Agent：
把 SDK / 云侧管理请求，转换成 Guest Linux 中真实的 命令、进程、文件与健康检查操作。
📍 运行在 Sandbox 内 🔌 默认管理端口 49983 ⌨️ commands / process 📁 filesystem ❤️ /health 🔐 用户 / UID / GID / Token

0先建立一个正确的心智模型

envd ≠ 沙箱本身。
envd 是装在沙箱里的“管理代理”，位于「外部 SDK / Agent Runtime」与「沙箱内部 Linux」之间。
不是 Sandbox
不是 Agent
不是 KVM / VMM
不是业务进程

1envd 在哪里？

最关键的层级关系：云侧负责“创建/调度/生命周期”，envd 负责“进入具体沙箱后，执行内部管理动作”。

外部调用方
Agent / 客户应用 / SDK
commands.run() · files.write() · API
腾讯云侧
Agent Runtime / AGS 控制面
创建 · 启动 · 停止 · 调度 · Token · 网络 · 生命周期
管理请求
Guest-side 管理代理
/usr/bin/envd
:49983
把结构化 SDK/API 请求翻译成 Guest OS 操作
Guest Linux
Linux 用户态环境
bash · python · node · java · /proc · /etc/passwd · filesystem
业务负载
Web / Agent / Notebook / 自定义服务
例如 8080 / 3000 等业务端口；与 envd 管理端口不是一回事。
结论：envd 更适合类比为“每台沙箱里都装了一个 Guest Agent”，而不是把它理解成整个沙箱。

2为什么沙箱需要 envd？

一个 Linux 沙箱被创建出来以后，只是一个执行环境。外部的高级 API 仍然需要一个“落地执行者”。

⌨️ 例 1：执行命令

sandbox.commands.run("python main.py")

这条高级 API 最终必须有人解决：

USER用哪个系统用户？UID/GID 是多少？ CWD工作目录在哪里？是否存在？ PATH命令从哪里查找？ ENVHOME / USER / LOGNAME / 注入环境变量是什么？ EXEC如何创建 Linux 子进程并返回 stdout / stderr / exit code？

→ envd 就是这层执行与转换组件。

📁 例 2：写文件

sandbox.files.write( "/workspace/hello.txt", "hello envd" )

内部实际面对的是：

1解析路径
相对路径 / HOME / 用户
2创建父目录
必要时 mkdir
3写入文件
Unix 文件权限
4设置 owner
必要时 chown

3envd 的核心能力

⌨️

命令 / 进程执行

  • 接收 command / args
  • 确定 user / cwd / PATH / env
  • 创建 Linux 子进程
  • 处理 stdout / stderr / exit
📁

文件系统操作

  • 读 / 写 / 上传 / 下载
  • 解析用户 HOME
  • 创建父目录
  • 按目标用户处理 ownership
❤️

健康检查

  • 默认管理端口 49983
  • 推荐探针 /health
  • AGS 通过健康探针判断实例是否可用
👤

执行上下文

  • /etc/passwd
  • UID / GID
  • HOME / USER / LOGNAME
  • defaultUser / defaultWorkdir（版本相关）
🔐

安全访问

  • Sandbox controller API 可受 access token 保护
  • 腾讯 AuthMode 可对 envd 49983 单独保持 Token 认证
⚙️

upstream 运行时能力

  • filesystem / process service
  • cgroup 管理
  • 端口扫描/转发等运行时组件
  • 当前 upstream 还包含 live-upgrade / handover 相关逻辑
边界提醒：“E2B upstream 当前源码具备的能力”不等于“腾讯修改版 v0.5.14 已全部支持”。腾讯场景应以腾讯版指南和实际产品行为为准。

4为什么 username / root / 权限这么重要？

username 不是一个“标签”

1username=user
2/etc/passwd
查询系统用户
3UID / GID
例如 1000 / 1000
4HOME
/home/user

腾讯指南要求：目标用户必须能被系统用户库查到，UID/GID 必须可解析；相对路径通常按用户 HOME 解析。

envd 以 root 启动 ≠ 业务一定 root 运行

envd · UID 0 root
拥有 setuid/setgid/chown 等更完整的管理权限
命令 A
以 user(1000) 运行
命令 B
以 sandbox(1001) 运行

root 启动 envd 的意义是让“管理代理”具备足够权限去代表不同用户执行操作，而不是要求业务代码都以 root 身份运行。

非 root envd 的典型限制：健康检查通常仍可工作；但切换到其他 UID、把文件 chown 给 root/其他用户时可能因 Unix 权限失败。上传失败还可能发生在文件已创建/截断之后，因此要注意副作用。

5为什么 49983 是“特殊端口”？

envd 管理端口 · 49983

TCP / HTTP 管理入口

  • 健康检查
  • 命令 / 进程管理
  • 文件系统管理
  • 属于高权限“控制能力”入口

业务端口 · 8080 / 3000 / …

业务流量入口

  • Web 服务
  • Agent 服务
  • Notebook / Preview
  • 安全语义与 49983 不同
腾讯云当前 AuthMode=PUBLIC 的官方定义明确区分了二者：envd 管理端口 49983 仍需 Token，其他端口可公开访问。这反映出管理端口与业务端口不同的风险级别。

6腾讯修改版：v0.2.11 vs v0.5.14

以下差异以你上传的《envd 使用指南》为基准，不用 upstream 新版行为反向覆盖腾讯版文档。

v0.2.11 旧版行为

命令执行
直接执行请求中的 cmd + args，不自动包一层 shell。
Shell 语法
管道、重定向、&&、通配符等需显式 /bin/bash -lc 或 /bin/sh -c。
/init
指南中描述为仅设置环境变量。
文件上传
/files 仅支持 multipart/form-data；不支持 application/octet-stream 原始 body。
OOM 行为
命令启动后会尝试写 /proc/<pid>/oom_score_adj；失败仅记录错误，不阻止命令继续。
VS

v0.5.14 指南推荐

命令执行
SDK 命令会被 envd 包装为 /bin/sh -c，并涉及 oom_score_adj 与 /usr/bin/nice。
镜像依赖
需要 /bin/sh、/usr/bin/nice，且相应 /proc/…/oom_score_adj 需要满足写入条件。
-cmd 参数
使用 /bin/bash -l -c；工作目录固定为 /home/user，因此需 bash 且目录存在。
默认用户
默认 root；可通过 /init 的 defaultUser 设置。
默认工作目录
支持 /init 的 defaultWorkdir。
文件上传
支持 multipart/form-data 与 application/octet-stream；后者需 path 查询参数。

7为什么经常这样启动？

/usr/bin/envd > /tmp/envd.log 2>&1 & exec node /app/server.js

逐段拆开

/usr/bin/envd启动沙箱管理守护进程。 > /tmp/envd.logstdout 写入 envd 日志。 2>&1stderr 合并到 stdout。 &envd 放到后台运行。 exec node...业务进程替换当前 shell，作为前台主进程。

容器内典型进程结构

/usr/bin/envd :49983
AGS 管理能力
node /app/server.js :8080
业务能力
注意：如果使用 /bin/bash -l -c 启动模板，最终镜像必须真的包含 /bin/bash。distroless / scratch / 极简镜像常常没有。

9从产品架构看，envd 属于哪里？

接入 / 控制面Agent / SDK / AGS API：创建、启动、停止、Token、调度、配置。
运行域 · 沙箱运行时envd：Guest Management Agent，承接管理请求。
Guest OS用户、UID/GID、进程、文件系统、/proc、shell、运行时。
业务负载Web / Agent / Notebook / Python / Node / Java 等实际服务。
产品定义建议：
“运行域 → 沙箱运行时 → 沙箱内管理代理（Guest Management Agent）”

问题正确理解
envd 是什么？沙箱内部管理守护进程 / Guest Management Agent。
它在哪里？运行在具体 Sandbox 的 Guest 环境内部。
谁调用它？SDK / 沙箱控制路径，用它把高级管理请求落地到 Linux。
最核心能力？命令/进程、文件系统、健康检查，以及用户/工作目录/环境上下文处理。
默认端口？49983。
为什么建议 root？为了更完整地执行 setuid/setgid/chown 等跨用户管理动作；不代表业务必须 root。
为什么业务活着仍可能沙箱不可用？业务进程和 envd 是两个角色；envd 未正常提供 49983 /health 时，AGS 管理能力可能失败。
腾讯版和 upstream 能否直接等同？不能。腾讯修改版行为优先看腾讯指南；upstream 只用于理解设计与演进。
